**Promise:** Set project milestones that each produce evidence about whether the project will reach done, so a problem shows up while it is still cheap to fix.

**Trap:** A milestone is a date on a plan; a date only says time passed, while a milestone should test whether the work is on track.

**Assumes:** teaching-leading/aligning-assessment.

## Outline

1. **A milestone is an assessment**: like a course task, it should ask for evidence of the outcome, at a lower level, earlier; "draft written" is activity, "a reader can follow the draft" is evidence.
2. **Aligning milestones to done**: each milestone maps to part of the definition of done; a milestone that maps to nothing is a status ritual.
3. **Riskiest part first**: order milestones so the most uncertain assumption is tested first, not the easiest piece.
4. **What a missed milestone tells you**: a miss is information about the plan, not a grade of the person; decide in advance what you will change if it slips.
5. **What this means for you**: for one current project, rewrite each milestone as "who sees what evidence", and move the riskiest test to the front.

## Key takeaways

- Write each milestone as evidence someone can inspect, not as a date or an activity.
- Put the milestone that tests the riskiest assumption first.
- Decide before the milestone what you will do if it fails; that turns a miss into a decision, not a blame session.
- A milestone that maps to no part of done can be dropped.
